# reports/ — 端到端评测的证据目录

这里存放 `run_benchmark.py` 的汇总产物。公开版只保留汇总报告；
原始 trace 与历史归档不随仓库发布，复现时可在本地重新生成。

## 目录结构与含义

| 路径 | 是什么 | 谁生成 |
|---|---|---|
| `benchmark_report.json` | **最新一次**跑分的汇总报告（固定名，便于引用） | `run_benchmark.py` |
| `<时间戳>_<通过>of<总数>.json` | 同上，但**带时间戳归档**，不会被下一次局部跑覆盖 | `run_benchmark.py` |
| `traces/`、`history/` | 原始调用语料与历史归档（公开版不包含；本地复现时生成） | `run_benchmark.py` / 手工归档 |

> ⚠️ `run_benchmark.py` 一律落两份报告（带时间戳 + 固定名）。这是踩坑后加的：
> 早先只有固定名，于是「4 用例的完整报告」被后来一次「`--only` 2 用例的局部跑」
> **静默覆盖**，仓库里只剩 2 个用例的记录。

## 怎么复现

```bash
# 1. 端到端跑分（真实 API，4 个用例约 ¥0.08）
python run_benchmark.py

# 2. 离线重放调阈值（零 API 成本，读上一步的语料）
python tools/replay_thresholds.py

# 3. 只跑部分用例（报告仍会带时间戳归档，不会覆盖完整记录）
python run_benchmark.py --only test_003_big_read
```

## 语料为什么要脱敏

`Trace.save()` 会把仓库绝对路径替换成 `<repo>`、家目录替换成 `~/`。
原因：agent 的 bash 输出里会带 `pwd` / 绝对路径（`ls`、`find` 的结果），
而语料是要入库的 —— 原样提交会暴露本机目录结构。

## ⚠️ 四个「校准数字」的区别（被追问时说清是哪一个）

它们**都不是错的**，但定义不同 —— 混着说会像数字打架。

| 数字 | 定义 | 出处 | 时期 |
|---|---|---|---|
| **1.858** | 最小二乘回归的**斜率**（`real = 309 + 1.858×est + 55.8×消息数`） | 历史基线（已归档） | 9-9，**旧**估算系数 |
| **3.0511** | **整体比值** `prompt_tokens ÷ est_tokens` | 历史基线（已归档） | 9-9，旧系数，**2 用例局部跑** |
| **1.3419** | **整体比值** `prompt_tokens ÷ est_tokens`（36992÷27566） | `benchmark_report.json` | 9-28，**新**系数，4 用例 |
| **0.959** | 最小二乘回归的**斜率**（`real = 454 + 0.96×est + 10.2×消息数`） | 9-28 校准记录（已归档） | 9-28，新系数 |

**怎么讲**：*"估算系数的修正是有前后对比的 —— 旧系数（0.25 token/字符）下回归斜率
1.858，说明系统性低估 86%；改成 CJK 感知估算后重跑，斜率降到 0.959（≈1，即基本吻合），
整体比值也从 3.05 降到 1.34。**斜率回到 1 附近就是『校准到位』的判据。**"*

## 关于压缩阈值的诚实说明

重放结果显示：**所有档位的触发率都是 0%**（无压缩上下文峰值 est 仅 3010 tk，
连 8000 都没到），脚本推荐 **8000**。实际取值 `16000 / 32000` 是
**等比重标定（×4）的工程裁量**，不是重放推导的最优解 —— 目的是在系数放大后
保持与旧版近似的触发行为，同时给长任务留余量。被追问时按这个口径答。

## 慢思考 A/B 实验（2026-09-28）

`benchmark.py` 里的 `enable_thinking` 原先**写死 `False`**，而 CLI 默认是**开**的 ——
也就是说此前所有跑分都是「快思考」口径，却被当成整体能力的证据。
现已加 `--thinking` 开关，两种口径都能跑、能对比：

```bash
python run_benchmark.py --report-dir reports/exp-nothinking            # A 快思考
python run_benchmark.py --thinking --report-dir reports/exp-thinking   # B 慢思考
```

**结果**（同一代码、同一环境、同一模型，各 4 个用例）：

| | A 快思考 | B 慢思考 | 差异 |
|---|---|---|---|
| 通过率 | 4/4 | 4/4 | **无差异** |
| 成本 | ¥0.0769 | ¥0.1187 | **+54%** |
| token | 41,452 | 64,023 | +54% |
| 耗时 | 43s | 62s | +43% |
| 校准系数 | 1.259 | 0.868 | 随模式变化 |

用例级最贵的一项：`test_002_code_gen` 从 ¥0.0277 涨到 ¥0.0539（**翻倍**，轮数 6 → 7）。

**这个结果应当怎么讲**：

- ✅ 「实测了代价：+54% 成本、通过率持平」—— 这是数据
- ❌ 「慢思考提升推理质量」—— 这组用例测不出来
- ⚠️ 也**不能反过来说「慢思考没用」**：4 个用例都是中等难度、快思考已全部通过，
  存在**天花板效应**，它在困难任务上的价值未被检验

**顺带一个观察**：校准系数随思考模式变化（快思考 1.259 / 慢思考 0.868）。
快思考下本地估算偏低 26%（压缩会稍晚触发）；慢思考下偏高约 13%（稍早触发，属安全方向）。
—— 引用校准系数时**必须带上口径**，否则同一个字段会给出两个值。

## 一个必须知道的浮动区间

同一份配置**重复跑**，数字会有几个百分点的浮动（LLM 输出本身不确定）。
实测快思考两次：**¥0.0754 / ¥0.0769**、校准系数 **1.342 / 1.259**。

所以引用数字时：
- 说「约 ¥0.08」，不说「恰好 ¥0.0754」
- 对比实验必须**同一天、同一代码**各跑一遍（本文 A/B 就是按这个规矩做的）

## 错误自愈 A/B 实验（2026-09-28）

自愈机制（20 个错误码 + 19 条救援提示 + 指纹死循环打断）**默认开启**。
`--no-recovery` 即为**基线组**：拿到裸错误、没有救援提示、没有死循环打断。

实验素材是 3 个**诱导失败**的容错用例（`test_005/006/007`，只在 A/B 时跑）：

```bash
python run_benchmark.py --only test_005_file_not_found --only test_006_multiple_match \
                        --only test_007_is_directory --report-dir reports/exp-recovery-on
python run_benchmark.py --no-recovery --only test_005_file_not_found --only test_006_multiple_match \
                        --only test_007_is_directory --report-dir reports/exp-recovery-off
```

**结果**（同一天、同一代码，各 3 个用例）：

| 用例 | 开自愈 | 关自愈 |
|---|---|---|
| test_005_file_not_found | 6 轮 / 9592 tk | 4 轮 / 5669 tk |
| test_006_multiple_match | 4 轮 / 5551 tk | 4 轮 / 6511 tk |
| **test_007_is_directory（唯一真正失败）** | **4 轮 / 6545 tk / 浪费比 0.64** | **6 轮 / 9181 tk / 浪费比 0.74** |
| 合计 | 3/3，¥0.0386，21688 tk | 3/3，¥0.0373，21361 tk |

**这个结果怎么讲（口径很重要）**：

- ✅ 能说：**在唯一一个真正失败的样本上，开自愈明显更省** —— 轮数 4 vs 6、
  token −28%、试错浪费比 0.64 vs 0.74
- ❌ 不能说「自愈让整体成本降低 X%」—— 合计差异（成本 −3.2%、token −1.5%）
  在噪声范围内，且失败样本 **n=1**
- ⚠️ 也不能说「自愈无效」—— 方向是正的，只是样本不够下统计结论

**用例设计踩过的坑**（写用例时值得先看一眼）：
1. 判卷**只认语义核心**，别卡格式 —— 曾要求 `SECRET-7749`，模型写了 `7749`，
   把「做对了」的用例判成失败
2. 诱导失败**不能靠提示** —— 给"请先确认"的提示，模型会先 read_file 从而避开失败；
   不给提示，它又可能直接不调工具。要靠**数据本身**（如文件里有两处相同文本，
   必然撞上 `EDIT_MULTIPLE_MATCH`）

**要让结论站得住**：需要更多稳定触发失败的用例（当前 3 个里只有 1 个），
且每个配置多跑几轮取平均。

> 附注：`CASES` 现在共 7 个（4 个常规 + 3 个容错）。主基准报告仍是 4 个常规用例；
> 容错用例默认只在 A/B 时用 `--only` 单独跑，避免把主基准的数字口径搞乱。
